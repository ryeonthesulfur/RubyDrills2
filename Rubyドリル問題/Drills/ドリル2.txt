============================================================

■ クラス・インスタンス
  class クラス名 ... end        → クラスの定義
  クラス名.new(引数)            → インスタンスの生成（initialize が自動で動く）
  @変数名                       → インスタンス変数（クラス内どこからでも使える）

■ initialize メソッド
  def initialize(引数) ... end  → .new 時に自動実行される初期化メソッド
  引数なしの initialize         → 空の箱を作るだけ。後からセッターで値をセット
  initialize(attributes = {})   → ハッシュをまとめて受け取る書き方（Rails の params に対応）

■ ゲッター・セッター
  def author; @author; end      → ゲッター（手書き）：外から値を読み取る
  def author=(v); @author=v; end → セッター（手書き）：外から値を書き換える
  attr_reader :name             → ゲッターを自動生成
  attr_writer :name             → セッターを自動生成
  attr_accessor :name           → ゲッター・セッター両方を自動生成

■ self
  self.author = 値              → initialize 内でセッターを呼ぶときに使う
                                   （self = 今まさに作られているインスタンス自身）

■ インスタンスメソッド
  def show ... end              → クラス内に出力処理を定義する方法
                                   （クラス内は @変数 で直接参照できるのでゲッター不要）

■ PHP対応メモ
  initialize                    → PHP では __construct
  attr_reader（ゲッター）       → PHP では手書きで getXxx() メソッドを定義
  attr_writer（セッター）       → PHP では手書きで setXxx() メソッドを定義
  #{@author}                    → PHP では {$this->author}
  string / : void               → PHP の型宣言（引数の型・戻り値の型を明示する）
  : void                        → 「何も返さない」を意味する戻り値の型宣言

■ Rails との関係
  Article.new(article_params)   → コントローラーから initialize を呼ぶ典型パターン
  initialize はモデル(M)のインスタンスを組み立てる工場の役割
  ActiveRecord::Base に高機能な initialize が内包されているため普段は見えない

【別解  PHP版：ゲッターを使って外から呼び出す場合の正しいコード】

class Article {
  // ① initialize の代わり（ここでインスタンス変数と同じものを作っている。）
  public function __construct(private $author, private $title, private $content) {
  }

  // ② attr_reader の代わり（PHPには自動生成機能がないので手書きする）
  public function getAuthor() { return $this->author; }
  public function getTitle() { return $this->title; }
  public function getContent() { return $this->content; }
}

// ③ Article.new の代わり
$article = new Article("阿部", "PHPの素晴らしさについて", "Awesome PHP!");


// ④ puts "著者: #{article.author}" の代わり
// ※PHPでは変数を {} で囲み、メソッドなので () を忘れずにつけます

echo "著者: {$article->getAuthor()}\n";
echo "タイトル: {$article->getTitle()}\n";
echo "本文: {$article->getContent()}\n";





    ＊＊まとめ＊＊

クラスの中に呼び出したい出力をメソッドで定義すれば、ゲッターメソッドは不要で、あとは外からその定義したメソッドだけ呼び出せばOKで、

一方で、 外で出力したい内容（呼び出し）を記述する場合には、クラスの中でそのデータの入ったメソッド（ゲッター）を定義しておく必要があるということ。

そしてそのゲッターメソッドの記述の仕方には、
Ruby においては、手書きで書く方法と、attr_reader でまとめて記述する方法の２種類があり、PHPにおいては、手書きする１種類しかないということ。

また、クラスの中で出力内容を定義してしまう場合において、Ruby では「#{@author}」という書き方をするけれど、 PHPにおいては、「{$this->author}」という書き方をする。

【PHP版】
class Article {
  // コンストラクタでプロパティを初期化
  public function __construct(private string $author, private string $title, private string $content) {}

  // ゲッター (読み取り用)
  public function getAuthor(): string { 
    return $this->author; 
    }

  // セッター (書き換え用)
  public function setAuthor(string $newAuthor): void {
     $this->author = $newAuthor; 
    }
}

$article = new Article("阿部", "PHPの素晴らしさについて", "Awesome PHP!");

echo "変更前の著者: {$article->getAuthor()}\n";         // ゲッターが呼ばれる
$article->setAuthor("田中");                           // セッターを呼び出して値を書き換える

echo "変更後の著者: {$article->getAuthor()}\n";

【補足3】PHPの型宣言（string, : void など）について

`string` や `: void` は、PHPの**「型宣言（タイプヒンティング）」**という機能です。
これは、変数やメソッドが扱うデータの「型」をあらかじめ決めておくことで、予期せぬエラーを防ぎ、コードを読みやすくするための仕組みです。

`public function setAuthor(string $newAuthor): void`

この一行を分解してみましょう。

1.  `(string $newAuthor)`：**引数の型宣言**
    これは「`setAuthor`メソッドは、引数として**必ず`string`型（文字列）のデータを受け取ります**」という宣言です。
    PHPでは、このように変数や引数の前に string や int などを書くことで、
    もし文字列以外のデータ（数値や配列など）を渡そうとすると、PHPがエラーを出してくれます。
    `$newAuthor` は、その受け取った文字列データを入れておくための変数名です。
    `setAuthor`は「値を書き換える」のが仕事なので、外から「新しい値」を受け取る必要があります。そのため、カッコの中に引数が書かれています。

2.  `: void`：**戻り値の型宣言**
    これは「この`setAuthor`メソッドは、処理が終わった後に**何も値を返しません（returnしません）**」という宣言です。
    `void`は「空っぽ」という意味の特別なキーワードです。
    値を書き換えるだけで、何かを報告する必要はないので `void` になります。

対照的に、`getAuthor()` メソッドは `public function getAuthor(): string` となっています。
これは「引数は何も受け取らないけれど、必ず`string`型（文字列）のデータを返します」という意味です。

【initialize メソッド   分解】

initialize メソッドというのは、クラスの外でオブジェクトを作り、かつ、そこに初期値を与えるセッターの２つの役割を担っている。

```Ruby
class Article

[ゲッター、セッターの記述]
  def author
   @author
  end

  def author=(new_author)
   @author = new_author
  end


  def title 
   @title
  end

  def title=(new_title)
   @title = new_title
  end


  def content
    @content
  end

  def content=(new_content)
     @content = new_content
  end



  # 引数なしのinitialize。まず「空の箱」を作る。
  def initialize
  end
end


# 1. まず空のインスタンスを作成
article = Article.new

# 2. セッターを一つずつ呼び出して値をセットしていく
article.author = "阿部"
article.title = "Rubyの素晴らしさ"
article.content = "Awesome Ruby!"
```


initialize メソッドに引数を与えない場合、それはオブジェクトを作るための起爆メソッドの意味だけになる。

「article = Article.new」でinitialize メソッドをよび、「article」というオブジェクトを作る。

本来ならば、

    article = Article.new("阿部", "Rubyの素晴らしさについて", "Awesome Ruby!")

というように実引数を用意するが、それをしない場合、initialize メソッドが下記のように
行っていたセッターの役割を分けた記述をする。


＊＊本来の書き方＊＊

  def initialize(author, title, content)
    @author = author
    @title = title          ⬅️これらがセッターの役割
    @content = content
  end

  本来の書き方では、データの代入をインスタンス変数でクラスの中に直書きしていたので、
  そもそもここに関しては、外から呼び出して代入するなどなかったため、ゲッターもセッターもクラスの中に記述する必要がなかった。


＊＊分解した書き方＊＊

# 2. セッターメソッドを一つずつ呼び出して値をセットしていく
article.author = "阿部"
article.title = "Rubyの素晴らしさ"
article.content = "Awesome Ruby!"


この分解した書き方はクラスの外側でするので、
「.author」という呼び出しや、呼び出して代入する「.author =」という書き方を可能にする
ゲッターとセッターの記述がクラスの中で必須になる。


ここまでのこと踏まえて、改めて、initialize メソッドを分解した書き方をすると以下のようになる。


```Ruby
class Article
attr_reader :author, :title, :content
attr_writer :author, :title, :content


  def initialize
  end
end

article = Article.new

article.author = "阿部"
article.title = "Rubyの素晴らしさ"
article.content = "Awesome Ruby!"
```




分解して、セッターの動きをもろに露呈させるとこうした動きしている。

これまでの書き方においては、initialize メソッドを書くことで、このセッターをある意味省いてたということ。

「article.author = "阿部"」の「.author =」がセッターがあることで可能で、

「#{article.author}」の「.author」はゲッターがあることで記述可能ということ。

こうしてみると、インスタンス変数というのは、オブジェクトの持つ属性としての核のようなデータというのが肌身でわかる。


いずれにせよクラスの中に出力内容をインスタンス変数で直書きすれば、
あとはそれを内包してるメソッドをクラスの外から呼び出すだけだからゲッターもセッターもいらない

ただし、もし、後から「やっぱり著者の名前を阿部から田中に変更したい」という仕様変更が出てきた場合は、その瞬間に、
初めて「書き換え」のためのセッター (attr_writer や def author=) が必要になる、という関係。


ゲッターの役割（読み取り） → show メソッドが担当している
セッターの役割（書き込み） → initialize メソッドが最初の1回だけ担当している（それ以降に書き換える場合は、セッターが別途必要になる）

【補足】forma_paramsのように、複数のデータをハッシュで渡して初期化する場合

あなたが以前学んだ「`Forma.new(forma_params)`の裏側で複数のセッターが呼ばれている」という動きを、
今見ている手書きの`Article`クラスで再現すると、以下のようになります。

ポイントは`initialize`メソッドの書き方です。


```Ruby
class Article

  def author
   @author
  end

  def author=(new_author)
   @author = new_author
  end


  def title 
   @title
  end

  def title=(new_title)
   @title = new_title
  end


  def content
    @content
  end

  def content=(new_content)
     @content = new_content
  end


  def initialize(attributes = {})
    self.author = attributes[:author]
    self.title = attributes[:title]
    self.content = attributes[:content]
  end
end


article_params = { author: "阿部", title: "Rubyの素晴らしさ", content: "Awesome Ruby!" }

article = Article.new(article_params)
```



「article_params」で、forma_params のようなハッシュを用意して、Article.new に渡す。

initializeメソッドでは、「(attributes = {})」と記述して、forma_paramsのようなハッシュを丸ごと受け取れるように変更。

渡されたハッシュの値を使って、対応するセッターを一つずつ呼び出している。これが「裏側でセッターが呼ばれている」の正体です。

「self」は「今まさに作られているインスタンス自身（この例では article ）」を指します。


puts "変更前の本文: #{article.content}"

# セッターを使ってインスタンスの本文を書き換える
# 1. 変数名を `article` に合わせる
# 2. 書き換えたい具体的な文字列を代入する
article.content = "Rubyは本当に素晴らしい！"

puts "変更後の本文: #{article.content}"

【応用】RailsのMVCとinitializeの関係

「アプリ開発で `initialize` メソッドなんて一回も見かけないんだけど、これってMVCでいうところのいわゆるどこの働きなの？」

これは非常に鋭い質問です。結論から言うと、`initialize` は **「コントローラー(C)」からの指示を受けて、
「モデル(M)」のインスタンスを生成する** という、CとMを繋ぐ非常に重要な働きを担っています。


    ・ではなぜ見かけないのか？
それは、普段私たちが使っている `ApplicationRecord` (もっと元を辿れば `ActiveRecord::Base`) という、
Railsが用意してくれている便利なクラスの中に、**超高機能な `initialize` メソッドが既に定義されているから**です。

MVCの流れで見てみましょう。

1.  **コントローラー (C)**
    `create` アクションなどで、`@article = Article.new(article_params)` というコードが実行されます。

2.  **モデル (M) の `new` が呼ばれる**
    この瞬間、`Article` クラスに隠されている（継承している）`initialize` メソッドが起動します。

3.  **隠された `initialize` の仕事**
    この `initialize` は、私たちが手書きした「ハッシュで初期化するパターン」と全く同じ動きをします。
    渡されてきた `article_params` というハッシュを元に、`self.author = params[:author]` のように、
    対応するセッターを次々と呼び出して、インスタンスの各属性に値をセットしていきます。

つまり、`initialize` は、**コントローラーが渡してきた設計図（`params`）を元に、
モデルのインスタンスという製品を組み立てる工場**のような役割を果たしているのです。
私たちはその工場の中身（`initialize` の中身）を直接見ることはありませんが、`Article.new` を呼ぶたびに、
その工場は確実に稼働している、というわけです。

【最終まとめ】Plain Ruby と Rails Controller の対比

これまで学んだことを、実際のRailsコントローラーのコードと並べて見てみましょう。
`Article.new`に渡すデータの形式が違うだけで、根本的な構造は全く同じです。

■ Plain Ruby (手書きのクラス)

# createアクションに相当する処理
# Article.newを呼び出し、データを渡す

    article = Article.new("阿部", "Rubyの素晴らしさについて", "Awesome Ruby!")



■ Rails Controller (実際のコード)

class ArticlesController < ApplicationController
  def create
    # createアクション
    # Article.newを呼び出し、paramsメソッドが返すハッシュを渡す
    @article = Article.new(article_params)
    # ...
  end

  private

  def article_params
    # paramsメソッド
    params.require(:article).permit(:author, :title, :content)
  end
end
