【解説】Railsにおけるインスタンス変数(@)とビューの関係

■ 1. なぜ update や destroy では @ が必須ではないのか？
update や destroy のようなアクションは、処理が終わった後に別のページへリダイレクト（移動）するだけで、専用のビュー（HTML画面）を描画しません。
ビューへデータを渡す必要がないため、本来はローカル変数（@なし）で処理を書いても全く問題なく動きます。
（※実務では before_action で set_article のように処理を共通化する都合上、結果的に @ をつけることがほとんどです）





■ 2. なぜビューにデータを渡す時だけ「@」が必要なのか？
結論から言うと、「コントローラーとビューは、別々のクラス（別々の部屋）」だからです。

・ローカル変数（@なし）の寿命
  ローカル変数は「そのメソッドが終わった瞬間に消滅する」という運命にあります。
  コントローラーの処理が終わってビューの部屋に移動する頃には、データは跡形もなく消えています。

・インスタンス変数（@あり）の寿命
  インスタンス変数は「そのクラスのインスタンスが生きている間は、ずっとデータを保持し続ける」という性質を持ちます。
  コントローラーの処理が終わっても、コントローラーの中にデータが残り続けます。





■ 3. Railsの裏側で起きている「宅配便マジック」
純粋なRubyのルールでは、いくらインスタンス変数であっても、他のクラスから勝手に中身を覗き見ることはできません（カプセル化）。
では、なぜ別クラスであるビューから @article が使えるのでしょうか？

それは、Railsのシステムが裏側で以下のような「お節介（魔法）」を焼いてくれているからです。

  1. コントローラーの処理が完了する。
  2. Railsが「コントローラーの中に @ がついた変数はないか？」と探し、回収する。
  3. 次にビューを描画するためのクラスを立ち上げる。
  4. 回収した @ 変数を、ビュークラスの中に無理やりコピー（注入）する。

つまり、Railsにとっての @ は、単なるインスタンス変数ではなく「このデータ、後でビューでも使います！という宅配便のラベル」として機能しています。





■ 4. バックエンド言語ごとのアプローチの違い
この「別々の部屋にどうやってデータを渡すか」というアプローチは、フレームワークによって思想が異なります。

・Rails（Ruby）のアプローチ：暗黙のコピー
  「@ をつけておいてくれれば、あとは裏側で空気を読んでビューに運んでおくよ！」という魔法のスタイル。

・Laravel（PHP）のアプローチ：明示的な手渡し
  魔法は使わず、最後にビューを呼び出すときに、ハッキリと手渡しするスタイル。
  
  // PHPの例
  public function show($id) {
      $article = Article::find($id);
      // 「view関数さん、$articleっていう荷物を持っていってね！」と明示する
      return view('article.show', ['article' => $article]); 
  }

どちらのアプローチであっても、「コントローラーとビューは別のオブジェクトである」というシステム構造の根本は世界共通です。
