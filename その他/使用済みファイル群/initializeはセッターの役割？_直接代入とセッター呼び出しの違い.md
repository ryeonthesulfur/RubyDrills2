# `initialize` はセッターの役割？
## 直接代入とセッター呼び出しの本当の違い

「`initialize` がセッターの役割をしているなら、中でセッターを呼ぶのは二度手間では？」  
この疑問は、クラス設計における「一貫性」と「安全性」を理解する上で非常に重要です。

## 1. 「裏口からの直接代入」とは？

まず、この考えは半分正しいです。`initialize` メソッドは、インスタンスが作られる際に初期値をセットする役割を持っています。

```ruby
def initialize(author, title, content)
  @author = author  # ①
  @title = title
  @content = content
end
```

この① のコードは、インスタンス変数 `@author` というデータボックスに、引数で渡された `author` の値を**直接**代入しています。

これは、言わば **「裏口からこっそり荷物を置く」** ような行為です。  
確かに荷物（データ）は置かれますが、もし正面玄関に「こういう荷物以外は受け付けません」というルールがあったとしても、それを完全に無視してしまいます。

---

## 2. `self.author = author` は「公式な窓口」を通す

一方、`self.author = author` という書き方は、インスタンス変数への直接代入ではありません。  
これは、**`def author=(value)` というセッターメソッドを呼び出す**ための、Rubyの特別な書き方です。

これは **「公式な窓口（セッター）に荷物を渡しに行く」** 行為です。

---

## 3. なぜ「公式な窓口」を通すのが重要なのか？

**「データの正しさを保証するルールを一箇所にまとめるため」** です。

例えば、「著者の名前は空っぽではいけない」というルールを追加したとします。  
このルールは、公式な窓口であるセッターメソッドに実装するのが最適です。

```ruby
class Article
  # 公式な窓口（セッター）
  def author=(new_author)
    # ルール：もし名前が空なら、エラーを出して処理を止める
    raise "著者名は空にできません" if new_author.nil? || new_author.empty?
    @author = new_author
  end

  def initialize(author, title, content)
    # ① 裏口から直接代入する場合
    # @author = author  # この書き方だと、上のルールは完全に無視される！

    # ② 公式な窓口を通す場合
    self.author = author  # この書き方なら、必ず上のルールがチェックされる！
  end
end
```

`initialize` の中で `self.author = author` と書くことで、インスタンスが作られる最初の瞬間から、必ず「名前は空ではいけない」というルールが適用されます。

直接代入してしまうと、`initialize` の時だけルールが無視され、後からセッターで変更しようとした時だけルールが適用される、という一貫性のない危険な状態になってしまいます。

---

## まとめ

| 書き方 | 種類 | 特徴 |
|:-------|:-----|:-----|
| `@author = ...` | 直接代入（裏口） | セッターに書かれたルールを無視するため、不正なデータを持つインスタンスが生まれる危険がある |
| `self.author = ...` | セッター呼び出し（公式窓口） | 必ずルールが適用されるため、インスタンスの正しさが常に保証される。**こちらが推奨されるベストプラクティス** |
